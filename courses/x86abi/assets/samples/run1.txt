3.  WHERE THE RETURN ADDRESS ACTUALLY IS

  %rsp mod 16 at a callee's FIRST instruction
    reached by a `call` that kept %rsp 16-byte aligned    8
    reached by a `call` with the `subq $8,%rsp` deleted  0
    %rsp at that point                               0x00007ffe6b972a38  (a STACK address)
    0(%rsp) at that point                             0x000056b02564ab5a  (a TEXT address)
    and the two are not within a few bytes of each other, which is the
    point: the word AT %rsp is not part of the stack.  It is the
    address `ret` will pop and jump to, and the control is that this
    function returned to its own caller rather than anywhere else.
    BOTH READINGS COME FROM ONE CALL, which is the only way a
    comparison between two readings of a register means anything.

  THE RETURN ADDRESS IS ON THE STACK.  `call` PUSHES it and `ret`
  POPS it, and nothing in the instruction needs a register for it.
  This is the measurement that decides a claim, and the claim it
  decides against is this course's own first draft.

3B. THE ONE INSTRUCTION THAT DOES TAKE A REGISTER: `syscall`.

  getpid() through libc                  = 1009620
  %rax after the bare `syscall`          = 1009620   match ? YES
  the instruction right after it         = 0x000056b02564ac35
  %rcx BEFORE the syscall                = 0x000076c5264ff70b
  %rcx AFTER  the syscall                = 0x000056b02564ac35
  %rcx == the address of the NEXT INSTRUCTION ?   YES
  %r11 after it, the RFLAGS `syscall` saved = 0x0000000000000202
  %r10 after it, my own marker              = 0xfeedfacecafebeef  survived ? YES

  SO HERE IS THE WHOLE OF IT, and it is two conventions and not one:

    an ordinary FUNCTION CALL passes its fourth integer argument
    in %rcx -- measured in section 2, 16 of 16 callers at four
    optimisation levels, v14=rcx in every one of them -- and it puts
    the return address ON THE STACK, as the table above shows.

    a SYSTEM CALL passes its fourth argument in %r10, because the
    `syscall` instruction itself writes the return RIP into %rcx,
    and the two measurements above are the proof: %rcx came back
    holding the address of the instruction that follows the syscall,
    bit for bit, and %r10 came back untouched.

  CAVEAT, and it is the whole limit of this section: this measures
  the INSTRUCTION.  Why Linux chose to renumber its argument list
  rather than save and restore %rcx is a decision recorded in the
  kernel, and this file cannot observe a decision.

4.  THE ALIGNMENT FAULT

  %rsp mod 16 at a callee's first instruction, four ways in:
    a `call`, %rsp 16-aligned at the call (the rule)         8
    a `call`, the `subq $8,%rsp` deleted                      0
    a TAIL `jmp`, no adjustment at all                       8
    a tail `jmp` after `subq $8,%rsp`                        0
    and that adjustment, left in place, kills the process: KILLED by a signal, because the return address is not where `ret` looks for it

  THE RULE IS TWO RULES AND NOT ONE.  A `call` pushes 8, so the
  caller's %rsp must be 16-ALIGNED at the call.  A tail `jmp` pushes
  nothing, so the jmpping function's %rsp must be 8 mod 16, which
  for a function entered at 8 mod 16 means NO ADJUSTMENT AT ALL.  A
  PLT stub is `endbr64; jmp *GOT(%rip)` and nothing else, and it is
  right for the same reason.

  one callee, three arms.  It is EXACTLY the prologue gcc -O0 emits:
  `pushq %rbp; movq %rsp,%rbp; subq $32,%rsp` and a 16-byte
  vector local at -16(%rbp), which is 16-byte aligned iff %rbp is,
  and %rbp is the CALLER's %rsp minus 8.

    movaps 16-byte store, CONFORMING call  -> returned, and the value read back was 0x3ff8000000000000
    movaps 16-byte store, VIOLATING call   -> KILLED by a signal
      signal 11, and 11 is SIGSEGV
    movups 16-byte store, VIOLATING call   -> returned, and the value read back was 0x3ff8000000000000

  THIS IS NOT A TIMING.  A misaligned 16-byte vector store on this
  machine is not slow, it is a FAULT, and the identical store in the
  unaligned-tolerant form goes through the same call untouched.  The
  rule exists because the fault exists, and the earlier course that
  measured unaligned loads found them FREE here, so the reason the
  rule was written cannot have been a penalty on this silicon.

  CAVEAT: what this cannot show is WHY the psABI says 16 and not 8.
  The 1997 drafts argued from SSE2's 16-byte moves, and this file has
  no way to observe a drafting argument.

5.  THE RED ZONE, MEASURED

  a leaf that writes 8 bytes at -8(%rsp) and 8 at -128(%rsp) and
  never touches %rsp at all.  The sum below is 0 only if BOTH
  words came back unchanged, so it is the checksum and the result
  in one number.

    leaf, no call, 2 slots written      every slot intact: YES -- both survived
    the same leaf, plus ONE `call`      every slot intact: NO -- at least one destroyed
    the same, plus a FRAMED callee      every slot intact: NO -- and this arm writes FOUR slots, not two

    The flag is 1 only if EVERY slot came back with the magic word,
    so a 0 is a measurement of destruction and not a measurement of
    silence, and the next block shows WHAT is in the first slot now.

  AND THE MECHANISM, PROVED RATHER THAN ASSERTED.  The leaf stores a
  magic word at its own -8(%rsp) and then calls a function that
  reports two numbers: its own %rsp, and 0(%rsp).
    the callee saw %rsp = 0x00007ffe6b972a40
    the callee's 0(%rsp)   = 0x000056b02564e071
    and 0x00007ffe6b972a40 is 8 BELOW the caller's own %rsp, which is where
    the leaf had put its data.  So:

      THE FIRST EIGHT BYTES OF THE RED ZONE ARE THE
      RETURN-ADDRESS SLOT, AND `call` WRITES THEM.

  That is the whole of the LEAF restriction, and it is not about
  128 bytes being tidy.  A function that uses the red zone and then
  makes a call has had the return address written over its own
  variable, and a function whose callee builds any frame at all has
  had its whole 128 bytes used as the callee's scratch space.

  CAVEAT, and it is the reason the psABI gives, which NOTHING HERE
  CAN MEASURE: the 128 bytes exist so that a leaf can be interrupted
  by a signal handler that uses the stack without the leaf having
  built a frame.  Whether a handler on this machine respects that
  reservation is a kernel property, and this process cannot find out.

6B. WHERE THE DIRECTION IS REVERSED, AND IT IS MEASURED.

      MXCSR before the call   0x00001fa0  rounding control 0
      MXCSR after  the call   0x00006000  rounding control 3
      MXCSR after  a clean one 0x00006000  rounding control 3
      x87 control word before 0x037f  PC 63, RC 0
      x87 control word after  0x0250  PC 16, RC 0

      MXCSR after the CALLER restored it  0x00001fa0  rounding control 0

  Note the field masks, because getting one wrong is how this file's
  first attempt at this experiment changed the ROUNDING mode while
  claiming to change the PRECISION mode, and why the x87 control word
  read back 0x0250 rather than the 0x0210 that was loaded: bit 9 is
  RESERVED and reads as 1 whatever you write.  The PC field is bit 8
  together with bits 0-5 -- and ONLY bit 8, so the mask is 0x0100 and
  not 0x0f00 -- and the RC field is bits 11-12.

  MXCSR's CONTROL BITS ARE CALLER-SAVED: a callee may change them and
  need not put them back, which is the OPPOSITE of the direction every
  general register obeys and the same direction the x87 control word
  obeys.  Two floating-point control registers, two directions, one
  ISA, and the difference is three instructions of setup.

  CAVEAT: what this cannot show is the COST of the reversal, and there
  is a real one: a function that rounds differently from its caller
  and does not say so is a wrong answer, not a slow one.

7.  THE VARARGS REGISTER SAVE AREA

  A fixed-arity function has nothing to describe: the callee KNOWS
  the types.  A variadic one does not, so the ABI has to describe
  itself, and the description is a 176-byte block of stack plus one
  integer in a register.

  The caller claims a number of vector registers in %al.  It claims
  honestly twice, so that the save area holds a KNOWN pair of values,
  and then it lies.

  honest, arm 1: 1.5 and 2.5
    al=2  a=0x3ff8000000000000 (1.500000)  b=0x4004000000000000 (2.500000)
  honest, arm 2: 101.25 and 202.5 -- these are now what the save
                area holds, and arm 3 is where it stops mattering
                what the caller put in xmm0 and xmm1.
    al=2  a=0x4059500000000000 (101.250000)  b=0x4069500000000000 (202.500000)
  LYING, arm 3: the caller puts 3.5 and 4.5 in xmm0 and xmm1 and
               then says it used NO vector registers:
    al=0  a=0x4059500000000000 (101.250000)  b=0x000000000000000a (0.000000)
               the FIRST of those, 0x4059500000000000, is 101.250000 -- bit
               for bit what arm 2 passed and NOT what this arm passed.
               The caller's values were not corrupted in transit; they
               were never looked at.  The consumer read the register
               save area, and the save area still held the last HONEST
               call.  The second slot is whatever was on the stack, and
               the al=1 arm below is the control: one is enough for gcc.
  al=1, arm 4: the same lie, understated rather than zero:
    al=1  a=0x400c000000000000 (3.500000)  b=0x4012000000000000 (4.500000)

  AND THE SAME FAILURE THROUGH THE C LIBRARY, because glibc's printf
  is a variadic consumer too and it obeys the same rule.  The caller
  here is hand-written assembly (abi_libc_printf) rather than inline
  asm, because the point is to put a CHOSEN value in %al, and because
  an inline-asm `call` inherits whatever %rsp the compiler had: the
  first version of this arm entered printf misaligned, and the
  symptom was fragments of other lines and then a crash rather than
  a diagnostic.  Section 4 is the same fault with a better witness.

glibc printf, al=2: 1.500000 2.500000
glibc printf, al=2: 101.250000 202.500000
  and now the same call with al=0, having been passed 3.5 and 4.5:
glibc printf, al=0: 101.250000 0.000000

  A number nobody passed, printed as though somebody had.  That is not
  a slow path and not a portability warning: it is a wrong answer,
  produced by a caller that broke one instruction's contract.

  CAVEAT: the psABI says %al is the NUMBER of vector registers used.
  gcc TESTS it for zero and spills all EIGHT when it is non-zero, so
  the al=1 arm above recovers both values and would still be a lie
  under the stricter reading.  A self-describing convention is still
  a convention: the description is there, and nothing checks it.

  THE CENSUS COLUMN IS THE POINT.  A checker that reports no
  violations and a checker that examines nothing produce the same
  line, and the second column is what tells them apart: this is
  how many functions actually WRITE each register, and how many of
  them save it first.  A zero in a violation column is only
  meaningful next to a non-zero in a census column.

  AND THE FLAGS ARE NOT ALL VIOLATIONS.  A function whose contract
  is to install a previously saved register context -- setjmp's
  family, backtrace, swapcontext -- is REQUIRED to destroy those
  registers, and a mechanical rule cannot know that.  A LEAF that
  clobbers a callee-saved register without saving it is legal only
  if the compiler knows no caller had a live value there, which is
  a fact about the CALLERS and not about this function.  Both
  exemptions are in the psABI and neither is checkable from inside
  one function, which is the honest limit of an ABI linter.

  AND THE TWO EXEMPTIONS OVERLAP, WHICH IS WHY THE REMAINDER IS
  COUNTED RATHER THAN SUBTRACTED.  A function can be a leaf AND a
  context-restorer -- setjmp is both -- so "the flags that are
  neither" is not flags - leaves - context.  The CLAPPERBOTH row
  above reports the overlap and the true remainder, and on this
  library the overlap is NON-ZERO -- which is a fact about glibc and
  not an arithmetic identity.

  It is zero on this library by luck, and a page that said
  "the other 148" without this row would have been right
  for the wrong reason.  A number that comes out right by
  coincidence is the one number worth re-deriving.

  THE POSITIVE CONTROL, without which every zero above is hollow:

10. RETRACTIONS.  Every one of these was asserted in a draft of this
    course, and every one is retracted here rather than softened.

   R1. "The fourth argument of a function call goes in %r10, because
        the hardware took %rcx for the return RIP."  RETRACTED, and
        the sentence is TWO errors welded together.  The fourth
        integer argument of an ordinary call goes in %rcx, measured
        16 of 16 callers at four optimisation levels.  And the return
        RIP is not in %rcx: `call` PUSHES it onto the stack, which
        section 3 reads out of a register.  What IS true is that a
        `syscall` instruction writes the return RIP into %rcx, and
        THAT is why the SYSTEM CALL convention renumbers its fourth
        argument to %r10.  Both halves measured, both halves in the
        same section, and the correct statement is the difference
        between two conventions rather than one fact.

   R2. "The red zone is 128 bytes of free scratch that a function can
        use like any other."  RETRACTED as stated.  It can use it and
        then it cannot make a call: the first eight bytes of the red
        zone are the return-address slot, `call` writes them, and
        section 5 proves it by reading the word back.  128 is a real
        number and the LEAF restriction is the whole of the content.

   R3. "The red zone costs nothing because it is 128 bytes of memory
        that was going to be cache lines anyway."  NOT CLAIMED.  This
        file does not time the red zone against a built frame, so it
        does not know, and the concept says so.

   R4. "The stack must be 16-byte aligned at every control transfer,
        including a tail call."  RETRACTED.  A `call` and a tail `jmp`
        want OPPOSITE adjustments, because a `call` pushes 8 and a
        `jmp` pushes nothing, and section 4 measures both.  A PLT stub
        is the proof: it is `endbr64; jmp *GOT(%rip)` and nothing else.

   R5. "%al holds the number of vector registers used, so a variadic
        callee reads exactly that many."  HALF TRUE AND THE WRONG
        HALF IS THE INTERESTING ONE.  gcc TESTS %al for zero and
        spills all eight when it is non-zero, so al=1 recovers a value
        that was passed in xmm1, as section 7 shows.  The convention
        is self-describing and the description is not enforced.

   R6. "glibc keeps %rsp 16-byte aligned at 99.2% of its call
        sites, so the remaining 0.8% is a list of bugs."  RETRACTED,
        and the number is a fact about the CHECKER rather than about
        glibc.  abilint.py loses track of %rsp at `pushfq`, at
        `enter`, and at any write it does not model, and a checker
        that cannot account for a mismatch is not evidence of a
        mismatch.  The alignment half of the linter is in this file
        and it is labelled unreliable where it is printed.

   R7. "A conforming C program cannot be miscompiled by a wrong
        calling convention, because the compiler and the ABI were
        written by the same people."  NOT A CLAIM AND NOT REFUTED.
        What section 2 establishes is narrower and is worth having:
        the emitted code matches a written specification at four

LIMITS, and each one names the thing that would settle it:

   ANY CYCLE COUNT.  There is no PMU on this machine, proved above by
      a child that ran RDPMC and died.  Every number in this file is
      a DURATION, and a duration bounds a count without measuring it.
   THE COST OF A VIOLATION.  The alignment rule is demonstrated with a
      FAULT, which is the right instrument, and the cost of merely
      misaligning something that does not fault is not measured here.
   WHETHER A SIGNAL RESPECTOR RESPECTS THE RED ZONE RESERVATION,
      which is the psABI's stated reason the red zone exists.  A
      kernel property, and this process cannot observe it.
   WHETHER GCC INTENDED ANY OF IT.  The corpus is real compiled code
      and the register assignments are real, but a claim about why
      the bytes are the bytes is not a claim about bytes.
   WHY THE psABI SAYS 16 AND NOT 8.  A drafting argument, and this
      file has no instrument for a drafting argument.
   WINDOWS x64, AND EVERY OTHER ABI.  Four integer registers instead
      of six, a 32-byte SHADOW SPACE the caller must allocate for the
      register arguments it is not using, and a different return
      convention.  QUOTED, NOT MEASURED.  There is no such machine in
      the room, and the next course in this section is about the
      x86-64 machine rather than about the other two architectures.

VERDICT.  What this artifact can support:
   - that the emitted argument assignment matches a written
     specification, by name, at four optimisation levels;
   - that the return address is on the stack and that `syscall`
     puts one in %rcx, which is why the two conventions differ;
   - that the alignment rule exists because a misaligned 16-byte
     vector store FAULTS, and that a call and a tail jmp want
     opposite adjustments;
   - that the red zone's first eight bytes are the return-address
     slot, and that a caller that lies about %al gets the previous
     call's floating-point arguments back;
   - that a function compiled without asynchronous unwind tables
     is invisible to a real unwinder, and what that costs a profile.
What it cannot support: any statement about a machine that is not this
one, any statement about cycles, and any statement about what the
compiler or the specification's authors were thinking.
